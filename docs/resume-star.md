## 版本 B：详细版（适合面试讲述 / Portfolio）

### S — Situation：项目背景与痛点

人形机器人（如 Unitree H1、Agility Digit）正在从实验室走向真实场景，但软件栈存在明显断层：

1. **任务层与执行层脱节**：高层自然语言指令（"去厨房把杯子拿来"）无法自动转换为底层关节轨迹
2. **缺乏自主故障恢复**：大多数系统遇到异常直接停机，没有分层级的自动恢复能力
3. **记忆割裂**：感知、规划、执行各模块各自维护状态，缺少统一的记忆架构支持长期推理
4. **单机孤立**：多机器人协作缺乏标准化的 Agent 间通信协议

**目标**：构建一个借鉴大模型 Agent 架构（LangGraph/LangChain）但针对**人形机器人物理约束**深度定制的垂直领域框架。

### T — Task：我的核心任务

- 从零设计框架整体架构，覆盖 11 个子系统
- 实现完整的 Agent 主循环（Perceive → Reflect → Plan → Act → Feedback → Recover）
- 构建五层记忆体系，支撑长期任务推理与经验复用
- 设计故障恢复系统，确保任何异常都有兜底路径
- 支持多机器人 A2A 协作，实现任务委托与协商
- 所有模块在无外部基础设施时可内存模式运行

### A — Action：关键设计决策与实现

#### 架构决策

```
┌─────────────────────────────────────────────────┐
│               FastAPI + WebSocket                │  ← 对外接口层
├─────────────────────────────────────────────────┤
│            LangGraph StateGraph                  │  ← 中枢编排引擎
│      (8 Nodes, 3 Conditional Edges)              │
├──────┬──────┬──────┬──────┬──────┬──────────────┤
│ 感知  │ 反思  │ 规划  │ 执行  │ 反馈  │ 故障恢复      │  ← 六阶段
├──────┴──────┴──────┴──────┴──────┴──────────────┤
│          五层记忆 + 上下文编译器                    │  ← 记忆系统
├─────────────────────────────────────────────────┤
│  A2A 协商 │ RabbitMQ │ ROS2 │ WebSocket │ MQTT  │  ← 通信层
└─────────────────────────────────────────────────┘
```

#### 1. 编排引擎 — 为什么是 LangGraph StateGraph

选择 LangGraph 而非手写状态机的原因：

- **原生检查点**：`PostgresSaver` 将每个节点的状态自动持久化，进程崩溃后可从断点恢复，无需额外开发
- **条件路由**：`add_conditional_edges` 将复杂的 if-else 逻辑声明式地表达为状态→目标节点的映射
- **子图组合**：将抓取序列（approach → execute → verify → retry）封装为可复用的子图

```python
# 核心路由逻辑 — 五路分支
graph.add_conditional_edges("feedback", route_after_feedback, {
    "continue": "perceive",   # 继续主循环
    "recover": "recover",     # 进入恢复链
    "delegate": "delegate_a2a", # A2A 委托
    "hri": "handle_hri",      # 请求人类帮助
    "complete": END,          # 任务完成
})
```

#### 2. 任务分解 — LLM + 模板双轨制

关键决策：LLM 不可用或输出不合法时自动回退到正则匹配的模板规划：

| 任务模式 | 触发词 | 生成结构 |
|---------|--------|---------|
| pick-and-place | pick up, grasp, grab | perceive → navigate → locate → grasp (4步) |
| navigation | go to, navigate to | perceive → navigate (2步) |
| search | find, look for, search | survey → search_pattern (2步) |
| generic | 其他 | perceive → speak_confirmation (2步) |

计划验证器执行 5 项检查：ID唯一性、DAG无环（DFS）、前置引用有效性、超时合理性、**双足平衡约束**（禁止同时行走和操作）。

#### 3. 人形机器人特有的状态建模

`HumanoidState` 扩展了通用 `RobotState`，新增：

| 字段 | 物理意义 | 用途 |
|------|---------|------|
| `zmp: (x, y)` | 零力矩点 | 稳定性判据，必须保持在支撑多边形内 |
| `cop_left/right` | 左右脚压力中心 | 检测足部接触状态 |
| `support_phase` | 支撑相 (double/left_single/right_single) | 决定是否能同时执行行走和操作 |
| `foot_contact_left/right` | 脚部着地状态 | 行走步态管理 |
| `head_pan_rad / head_tilt_rad` | 头部云台角度 | gaze_at 技能控制 |
| 双臂独立位姿 + 力传感器 | 左右臂分别建模 | 交接、双手操作需要独立力感知 |

#### 4. 五层记忆架构的设计哲学

每层记忆有明确的时间尺度、数据形式和查询方式：

| 层级 | 时间尺度 | 存储 | 查询方式 | 典型容量 |
|------|---------|------|---------|---------|
| 工作记忆 | 秒级 | Redis Hash (TTL=10s) | Key-Value 精确查 | 当前状态 + 200 事件缓冲 |
| 情景记忆 | 任务级 | PostgreSQL JSONB | 全文搜索 + 条件过滤 | 全部历史任务 |
| 语义记忆 | 跨任务 | Milvus 向量 | COSINE 相似度 | 嵌入向量无上限 |
| 空间记忆 | 环境级 | 内存地图 | 房间图 BFS | 房间 + 物体位置 |
| 知识库 | 永久 | PostgreSQL | 精确 Key 查询 | 结构化领域事实 |

**上下文编译器**将这五层输出统一编译为 LLM 提示词，让规划拥有"过去的经验 + 当前的状态 + 环境的约束 + 安全的底线"。

#### 5. 故障恢复 — 责任链模式

```
SelfDiagnose    → 处理通信/感知错误（重连传感器）
    ↓ 失败
RePlan          → 处理运动学/动力学/规划错误（重新分解任务）
    ↓ 失败
RetrySkill      → 调整参数重试（换手/降速/扩大搜索）
    ↓ 失败
SafeStop        → 处理安全/硬件错误（急停+安全姿态）
    ↓ 失败
HumanHelp       → 最后防线（组装详细消息推送操作员，始终 can_handle=True）
```

**关键决策**：`HumanHelp.handle()` 返回 `success=True`。从恢复链的视角，成功地将问题升级给正确的一方（人类）就是成功的处理，否则链会进入无意义的 `exhausted` 状态。

#### 6. 无基础设施即可运行

每个记忆模块和后端通信组件都有**进程内回退**：
- 工作记忆：Redis → dict + deque
- 情景记忆：PostgreSQL → dict
- 语义记忆：Milvus → list + 手动余弦相似度
- 安全监控：`is_safe` 默认返回 True（模拟模式）

这意味着开发者可以在没有任何基础设施的情况下运行和测试完整框架。

## 面试可能追问 & 回答思路

**Q1: 为什么不用 ROS 2 的行为树，而要自己造 LangGraph？**
> 行为树适合底层运动控制的有序组合，但处理"目标物体不见了→重新搜索→搜索失败→换一个房间→最终找人类帮助"这种**多层次、需要历史记忆和 LLM 推理**的决策流非常笨拙。LangGraph 的状态图 + 自然语言 LLM 分流 + 条件路由正是为此设计的。ROS 2 桥接层在框架中保留了接口，底层关节控制仍然走 ROS 2。

**Q2: 五层记忆每一层是必须的吗？会不会过度设计？**
> 每层解决不同时间尺度和查询方式的问题。工作记忆（秒级状态）和情景记忆（任务级历史）是基本需求。语义记忆解决了"从几千个历史任务中找到最相似的 5 个"的高维检索问题——这是传统数据库做不到的。空间记忆是导航的基础。知识库存储了物体可供性、安全规则等不随时间变化的硬知识。去掉任何一层都会在某个场景下暴露短板。

**Q3: 故障恢复为什么是链而不是图？**
> 图（多个恢复路径同时尝试）在机器人场景中有物理冲突风险——不能同时执行 SafeStop 和 RetrySkill。链的简化恰恰是对的：从代价最低的修复开始，逐级升级到代价最高的（人类介入）。这也是人形机器人领域的最佳实践。

**Q4: 人形机器人和轮式机器人在 Agent 框架设计上有什么本质区别？**
> 核心是**稳定性约束**。人形必须时刻保持 ZMP 在支撑多边形内，这意味着不能同时行走和精细操作——这是在 PlanValidator 中硬编码的检查。轮式机器人不需要担心这些，但人形的"全身协调抓取"（bend knees + lean + reach）比机械臂的独立运动复杂得多，需要 `whole_body_grasp` 这种将平衡和操作耦合的技能类型。
